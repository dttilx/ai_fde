# APX-240 故障诊断 Agent Constitution

## Core Principles

### I. Safety and Evidence First (NON-NEGOTIABLE)

安全规则和可验证证据优先于模型常识、历史相似度和用户期望。系统必须遵守 APX-240 说明书 SAFE-01 至 SAFE-05：出现烟雾、焦味、异常高温、剧烈振动、金属摩擦声或部件松脱时，必须立即停机并升级专家；打开防护罩、清除夹料、检查线路或接触加热组件前，必须断电、锁定、挂牌并确认残余能量释放；禁止短接安全门、绕过报警、带电插拔线路、带电拆线、带压拆装或徒手接触加热部件。涉及线路、加热回路、伺服、气路拆装或安全联锁时，必须由相应授权人员处理。

任何故障判断、可能原因、排查步骤和升级判断都必须能够追溯到用户输入、已确认的多模态证据、设备说明书、报警码、历史案例、维修记录或已审核案例。证据不足、知识库无覆盖、风险无法判断或证据互相矛盾时，系统必须停止进一步危险排查并升级专家。

### II. Multimodal Evidence Must Be Reviewable

文字、结构化报障、图片、OCR、视频和 QR 都是故障事件的输入来源。图片、OCR、视频和 QR 处理器只能生成候选证据，不得自动把候选结果写成事实。每个候选结果必须支持接受、人工修正和拒绝；只有确认后的证据才能进入诊断上下文。

系统必须保留证据来源、置信度、时间、媒体引用和必要的图像区域或视频时间范围。图片模糊、过暗、遮挡、未覆盖相关区域、OCR 无法读取或视频无法判断时，必须明确说明无法判断及补拍或补录要求。QR 只用于定位设备资产和关联历史记录，不得单独证明故障原因。

报告必须严格区分已知事实、模型观察、可能原因、未确认信息和矛盾信息。报障人的推测不能改写成确定事实；模型不能补全缺失的读数、时间、维修结果或设备状态。

### III. Bounded Agent and No Direct Equipment Control

Agent 必须采用有界状态图或等价的有限编排流程，限制最大步骤、检索轮次、工具调用次数、Token 数量和执行超时。允许的决策动作仅包括继续检索、请求补充信息、升级专家和生成最终报告。达到预算后必须输出当前可确认信息和停止原因，不得无限循环或继续猜测。

Agent 只提供诊断、证据解释、安全前置条件、排查顺序和升级建议，不得直接启停设备、修改热封温度或气压、调整伺服参数、发送 PLC 指令或执行任何维修动作。AI 只能提出可能原因，不能自动确认最终根因。

### IV. Layered Knowledge and Traceable Versions

安全规则、报警码、设备手册、历史案例、维修记录、设备资产和已确认案例必须逻辑隔离。第一阶段使用结构化规则、关键词检索和向量检索组成混合 RAG；不强制引入完整 GraphRAG，也不得把所有资料混成无法解释的单一向量库。历史案例和维修记录只能提供参考，不能覆盖当前现场证据或安全规则。

每次诊断必须记录 Agent 图版本、Prompt 版本、模型版本、知识索引版本、输入证据快照、检索结果和引用来源。报告中的每个可能原因必须关联具体报警码、说明书章节、历史案例或维修工单。原始资料、解析结果、切块、引用和索引发布必须具有可追溯的版本关系。

### V. Human Confirmation and Append-Only Learning

涉及高风险、证据矛盾、知识库无覆盖或授权边界的问题，系统必须进入专家接管状态。专家修订、维修反馈和后续诊断必须生成新版本，不得覆盖原始证据或原始 AI 报告。

现场维修结果可以形成候选案例，但只有工程师或专家确认根因、维修动作和复机验证，并完成审核后，才能进入正式案例知识库。未经审核的原始事件、模型推断和质量反馈不得自动污染生产 RAG。质量反馈必须追加保存，并绑定对应诊断运行、模型版本、Prompt 版本和知识索引版本。

## Additional Constraints

### Safety and Scope Constraints

- 系统必须将安全规则作为独立的前置判断层，不能只依赖大模型提示词。
- 任何排查步骤必须遵循 APX-240 报警码给出的安全顺序。
- 高风险场景必须显示停机动作、禁止动作、授权角色和升级依据。
- 第一阶段必须支持文字和结构化报障，并纳入图片、OCR、视频和 QR 的证据管线；多模态识别失败时必须可降级到文字输入。
- 系统不建设完整 MES、SCADA、EAM、PLC 控制或自动维修能力。

### Architecture Constraints

- 第一阶段采用模块化单体后端，至少划分事件、证据、安全、诊断、知识、专家和反馈模块。
- RAG 必须支持安全规则、报警码、设备手册、历史案例、维修记录和已确认案例的逻辑分层。
- GraphRAG 不是第一阶段硬性依赖；如建立关系图，只能作为结构化关系和可解释检索增强，不得替代安全规则和精确报警码匹配。
- API、模型调用、检索和持久化必须通过明确的服务接口隔离，路由层不得直接实现诊断业务逻辑。
- 所有诊断报告必须使用结构化数据契约，同时提供适合工程师阅读的界面呈现。

### Output and Acceptance Constraints

每次诊断至少必须输出以下字段：

- 故障现象；
- 已知事实；
- 可能原因；
- 证据来源；
- 安全前置条件；
- 排查顺序；
- 需要补充的信息；
- 停止条件/是否升级专家。

以下场景属于最低验收集合：

1. A203 信息完整时，引用报警码 A203、历史案例 H02 和相关维修工单，并将 H1 加热回路开路标记为可能原因而非已确认根因。
2. A310 信息不足时，主动追问上游压力、设备端压力和漏气证据，不直接断定下游接头松动。
3. SAFE-01 高风险场景立即要求停机并升级专家，禁止继续普通排查。
4. 图片、OCR、QR 候选证据支持接受、修正和拒绝，并将识别失败明确呈现为无法判断。
5. 维修结果具备确认根因、维修动作和复机验证后，才能形成待审核或已审核案例。

## Development Workflow

### Specification Before Implementation

任何新功能必须先更新或创建功能规格，再制定技术方案、数据模型、API 契约、验收场景和任务清单。实现阶段必须以已批准的规格、方案和任务为依据；需求、架构或安全边界发生变化时，先更新规格制品，再修改代码。

### Evidence-Driven Validation

每个核心能力必须至少有一个可执行验收场景。诊断、检索、安全和多模态功能必须验证正常路径、信息缺失路径、证据冲突路径和高风险路径。验证结果必须记录输入、期望行为、实际输出和使用的版本。

### Review Gates

进入实现前必须检查：范围是否仍限于 APX-240 题目、是否违反安全原则、是否引入不必要的基础设施、是否定义了失败和无法判断状态。完成实现后必须检查：报告字段完整性、引用有效性、状态机合法性、专家修订不可覆盖、未审核事件未进入生产知识库。

### Simplicity and Maintainability

优先使用现有框架和直接的模块接口。只有在明确解决检索质量、证据可追溯性、安全控制或现场体验问题时，才引入新基础设施。GraphRAG、视频音频深度分析、离线工作包和多设备族支持应在核心诊断闭环稳定后再增加。

## Governance

本 Constitution 是项目的最高开发约束。功能规格、技术方案、任务清单、代码、测试和部署配置都必须遵守其中的安全、证据、范围和版本要求。

任何修改必须：

1. 说明修改的原则、理由和影响范围；
2. 检查是否改变既有安全边界或验收承诺；
3. 更新版本号和最后修订日期；
4. 同步更新受影响的规格、方案、任务和验收材料；
5. 在实现前由项目负责人确认重大原则变化。

版本规则遵循语义化版本：

- MAJOR：删除、重定义或放宽不可违反的核心原则；
- MINOR：新增核心原则或新增实质性治理约束；
- PATCH：文字澄清、格式调整或不改变治理含义的修订。

每次代码评审或功能验收都必须检查 Constitution 合规性。任何违反安全优先、事实边界、人工确认或版本可追溯原则的实现都不得进入可演示版本。诊断质量反馈和维修结果只能作为后续规格修订和审核案例的输入，不能绕过本治理流程直接改变生产行为。
